# clails セッション・認証ガイド

## 概要

clails には、[`lack-middleware-session`](https://github.com/fukamachi/lack)
をベースにした Cookie セッションの段と、そのセッションの上に構築された
小さな `current-user` 拡張ポイントが用意されています。

まず押さえておきたい既定値が2つあります。

- **`clails new` で生成したプロジェクトでは、セッションは有効になっています。**
  有効化している行は `app/config/environment.lisp` にコメント付きで書かれて
  おり、最初のリクエストから `(session controller)` が使えます。
- **フレームワーク本体の既定は「無効」です。** セッションについて何も書いて
  いない既存プロジェクトの挙動は一切変わりません(Cookie は発行されず、
  `(session controller)` は「段を有効にしてください」というエラーになります)。
  今回の変更が既存プロジェクトに自動的に及ぶことはありません。
  [12. 既存プロジェクトの移行手順](#12-既存プロジェクトの移行手順) を参照してください。

clails が提供するもの／しないもの:

- **セッション機能** はフレームワークが提供する実質的な機能です。リクエスト
  ごとの Cookie ベースのハッシュテーブルに加えて、サーバ側の有効期限、
  掃除、セッション単位のロック、ストアの差し替えを提供します。
- **`current-user`** は「配線」のみです。clails はパスワードのハッシュ化、
  ログイン/ログアウト用ルーティング、「ユーザー」モデルの規約など、認証の
  仕組みそのものは一切提供しません。「現在ログインしているユーザーが誰か」
  を保存するための、ドキュメント化された置き場所を提供するだけです。
  ログインロジックはプロジェクト側で実装し、成功したら
  `(setf (current-user controller) ...)` を呼び出します。

明示的に **対象外**(clails が提供しないもの):

- Remember-me(永続ログイン)トークン
- OAuth / OIDC 連携
- ロールベースの認可・パーミッションチェック
- 組み込みのパスワードハッシュ化ヘルパー

### CSRF 対策

**生成されたプロジェクトでは CSRF 検証も有効になっています。** 状態を変える
要求 — POST・PUT・PATCH・DELETE — はすべてこのセッションのトークンを伴わな
ければならず、伴わない要求には 403 を返し、それを `:audit` の口に記録します。
GET と HEAD は検証しません。

セッションと同じく、**フレームワーク自身の既定は無効** です。既存プロジェクト
は設定を足すまで影響を受けません。

フォームを書く前に知っておくべきことが2つあります。

- **隠しのトークン欄を自分で書かないでください。** フォームヘルパ
  (`form-tag`、`form-with`)が書きます。生成されるビューの名前空間は既に
  これらを取り込んでいます。[9. CSRF 対策](#9-csrf-対策) を参照してください。
- **特定の経路だけ検証を免除する方法はありません。** 検証を有効にすると
  *すべての* エンドポイントが検証対象になります。
  [9.6 検証の免除は提供しません(その代償)](#96-検証の免除は提供しませんその代償)
  を参照してください。

## 1. 設定

セッションの設定項目はいずれもセッション専用のパッケージで宣言され、
`clails/middleware/session-middleware` から再公開されています(さらに
`clails/middleware` からも再公開されています)。したがって1つのパッケージで
すべてに到達できます。

**これらはすべて `clails server` がミドルウェアスタックを組み立てるときに
1度だけ読まれます。** 設定は `app/config/environment.lisp`(サーバ起動前に
読み込まれるファイル)に書いてください。稼働中のイメージで値を変えても、
動いているサーバの応答は変わりません。

### 生成されたプロジェクトに入っている内容

```common-lisp
(in-package #:myapp/config/environment)

;; clails の Cookie セッションの段を有効にする
(setf *enable-session-middleware* t)

;; NIL = clails のインメモリストア(DB ストアは第6節)
(setf *session-store* nil)

;; 放置されたセッションが失効するまでの秒数
(setf *session-idle-timeout* 1800)

;; 失効したセッションは定期掃除でも削除される
(setf *session-sweep-enabled* t)
(setf *session-sweep-interval* 300)

;; 状態を変える要求をこのセッションの CSRF トークンで検証する
(setf *enable-csrf-middleware* t)
(setf *csrf-form-token* "_csrf_token")     ; 隠し欄の名前
(setf *csrf-header-name* "X-CSRF-Token")   ; fetch/XHR 向けのヘッダ
(setf *csrf-one-time-token* nil)           ; トークンを使い回す(9.4 節)

;; PUT / PATCH / DELETE を意図する用紙が使う "_method" 欄。この段は既定で
;; 有効なので有効化の行はありません。生成される設定は欄の名前を書き、
;; 無効化の方法を注釈で説明するだけです。
(setf *method-override-parameter* "_method")
```

**環境ごとに値が異なる設定は2つあります** — Cookie の安全通信限定(Secure)と
構成の整合検査の厳しさ(strict)です。生成される設定ファイルでは両方を環境ごと
の関数(`setup-environment/develop`、`setup-environment/test`、
`setup-environment/production`)に分けており、`clails.boot` が `CLAILS_ENV`
を解決したあと、ミドルウェアスタックが組み立てられる前に
`initialize-environment-config` を呼び出します。
[2. セッション Cookie](#2-セッション-cookie) と
[11. 構成の整合検査(strict)](#11-構成の整合検査strict) を参照してください。

### 設定項目一覧

| 設定項目 | 意味 | フレームワーク既定値 | 推奨値 |
|---|---|---|---|
| `*enable-session-middleware*` | セッションの段が機能するかどうか | `NIL`(無効) | `T` — 生成プロジェクトは設定済み |
| `*session-store*` | セッションの保存先。`NIL` はインメモリストア | `NIL` | 開発はインメモリ、本番は DB ストア |
| `*session-state*` | Cookie。`NIL` は clails 自身の状態(下の Secure を反映) | `NIL` | Cookie 名・パス・ドメイン・SameSite を変えたいとき以外はそのまま |
| `*session-cookie-secure*` | Cookie に Secure を付ける(HTTPS 以外では送られない) | `NIL` | HTTPS で公開する環境では `T`、平文の開発・試験では `NIL` |
| `*session-idle-timeout*` | 放置してよい秒数。`NIL` でサーバ側の失効を無効化 | `1800`(30 分) | 1800。機密性の高い用途ではより短く |
| `*session-sweep-enabled*` | 定期掃除スレッドを動かすか | `T` | `T` |
| `*session-sweep-interval*` | 掃除の間隔(秒) | `300`(5 分) | 300。間隔を延ばしても失効済みセッションが有効になることはない |

セッションと組になる2つの段の設定項目:

| 設定項目 | 意味 | フレームワーク既定値 | 推奨値 |
|---|---|---|---|
| `*enable-csrf-middleware*` | 状態を変える要求をセッションのトークンで検証するか | `NIL`(無効) | `T` — 生成プロジェクトは設定済み |
| `*csrf-form-token*` | トークンを読む隠し欄の名前 | `"_csrf_token"` | そのまま(`form-tag` が出力する名前) |
| `*csrf-header-name*` | トークンを代わりに入れてよいヘッダ | `"X-CSRF-Token"` | そのまま |
| `*csrf-one-time-token*` | 検証成功時にトークンを使い切る | `NIL`(使い回す) | `NIL`。変える前に [9.4](#94-使い切り方式を選ぶ場合の代償) を読むこと |
| `*csrf-session-key*` | トークンを置くセッションのキー | `"clails.csrf-token"` | そのまま(予約キー。第3節) |
| `*csrf-forbidden-message*` | 拒否した要求に返す 403 の本文 | `"Forbidden: invalid CSRF token. Reload the page and try again."` | そのまま、または訳す |
| `*enable-method-override*` | POST が本文で別の操作種別を宣言できるか | `T`(有効) | `T`。`NIL` にするのは、同じ道筋に POST の経路と PUT/PATCH/DELETE の経路を両方書いている手書きの経路表だけ(第10節) |
| `*method-override-parameter*` | その隠し欄の名前 | `"_method"` | そのまま |
| `*strict-configuration*` | 動きえない構成で中止するか、警告して続行するか | `T`(中止) | 本番は `T`、開発と試験は `NIL` — 生成プロジェクトがそう書きます(第11節) |

`*enable-csrf-middleware*` ほか `*csrf-…*` は
`clails/middleware/csrf-middleware`、読み替えの2項目は
`clails/middleware/method-override-middleware`、`*strict-configuration*` は
`clails/environment` で宣言されています(1つの段の話ではないため)。いずれも
`clails/middleware` からも再公開されています。

セッションの段は常にミドルウェアスタックの決まった位置にあります(トランザ
クションの段と振り分けの段より外側でなければならないため)。したがって
セッションを有効にするために `*clails-middleware-stack*` を編集する必要は
ありません。`*enable-session-middleware*` が `NIL` のときは単なるパススルー
です。スタック全体については [環境設定ガイド](environment_ja.md) を参照して
ください。

## 2. セッション Cookie

clails が既定で発行する Cookie は次の形です。

```
_session_id=<16 進 40 文字>; path=/; HttpOnly; SameSite=Lax
```

- **HttpOnly** — スクリプトからセッション ID を読めません。
- **SameSite=Lax を明示** しています。属性を省略することは「未指定」には
  なりません。下位の応答組み立てが `None` を既定にし、さらに毎回警告を出す
  ためです。
- **実装を推測されない Cookie 名。** 以前の既定値は下位ライブラリ由来の
  `lack.session` で、応答を見た相手にどのライブラリ(つまりどの既知の弱点)を
  試せばよいかを教えてしまっていました。
- **失効日時は意図的に持ちません。** 期限はサーバ側の放置時間(第5節)です。
  Cookie 側で同じ方針は表現できません。段が `Set-Cookie` を付けるのは
  セッションの作成時・ID 変更時・破棄時だけなので、Cookie に置いた日時は
  更新されず、「作成時刻からの絶対期限」になってしまいます。ブラウザから
  見ればこの Cookie はセッション Cookie(ブラウザを閉じると消える)であり、
  サーバ側の放置時間だけが期限として働きます。

### Secure: 環境ごとに値が変わる唯一の設定

`T` にすると、ブラウザはこの Cookie を **HTTPS でのみ** 送信します。
フレームワークの既定は `NIL` で、これは「既定を安全側に寄せる」ことからの
意図的な例外です。Secure 付きの Cookie は平文 HTTP では **まったく** 送られ
ないため、TLS なしで動かす開発環境でこれを有効にするとセッションが成立しなく
なります(Cookie は発行されるが戻ってこないので、毎回が初回訪問に見えます)。

**clails は実行中の環境を判定しません。** `*session-cookie-secure*` だけを
読みます。だからこそ環境差はプロジェクトの設定ファイルが担います。

```common-lisp
(defun setup-environment/develop ()
  (setf *session-cookie-secure* nil)    ; 平文 HTTP
  (setf *strict-configuration* nil))    ; 第11節

(defun setup-environment/test ()
  (setf *session-cookie-secure* nil)    ; 平文 HTTP
  (setf *strict-configuration* nil))

(defun setup-environment/production ()
  (setf *session-cookie-secure* t)      ; HTTPS のみ
  (setf *strict-configuration* t))
```

**この既定と strict の既定が逆向きである理由。** `*strict-configuration*` は
*安全側* が既定で、`*session-cookie-secure*` は *非安全側* が既定です。
一貫していないように見えますが、そうではありません。strict を安全側の既定に
しても、動いていたものは何も壊れません — そもそも要求を処理できない構成で
しか発火しないからです。一方 Secure を安全側の既定にすると、平文 HTTP で
動かすすべての開発環境が、しかも無言で壊れます。それぞれの既定は「間違って
いたときに何を失うか」で選ばれており、逆向きにしたときに得られたはずの
利便性は、上のファイルで環境ごとに与えています。

### Cookie を変更する

```common-lisp
(setf clails/middleware/session-middleware:*session-state*
      (clails/middleware/session/state/cookie:make-clails-cookie-state
        :cookie-key "_myapp_session"
        :path "/"
        :samesite :strict))
```

自分で組み立てた状態は `:secure` を自分で持つため、
`*session-cookie-secure*` は参照されなくなります。ここには lack 自身の
Cookie 状態も渡せます。ブラウザを閉じても残る **永続 Cookie** が必要な場合は
そちらを使ってください(clails の状態は意図的に表現できません)。いずれの
場合もサーバ側の放置時間は適用されます。

## 3. セッションデータの読み書き

コントローラのインスタンスには `session` アクセサがあり、Cookie セッション
に紐づくリクエストごとのハッシュテーブル(`:test 'equal`)を返します。

```common-lisp
(defmethod do-get ((controller <my-controller>))
  (let ((visits (or (gethash "visits" (session controller)) 0)))
    (setf (gethash "visits" (session controller)) (1+ visits))
    (set-view controller "home/index.html"
              `(:visits ,(gethash "visits" (session controller))))))
```

ハッシュテーブルに入れた値は応答の生成後にストアへ書き戻され、クライアント
は Cookie を保持し続けるので、次のリクエストでも同じ内容を読めます。

`*enable-session-middleware*` が `NIL` のとき `(session controller)` は
エラーになり、段を有効にするよう案内します。黙って使い捨てのハッシュテーブル
を返すと、気づかないままデータを失いやすいからです。

### 予約キー: `clails.` 接頭辞

**`clails.` で始まるキーは枠組みのものです。** アプリケーションから書き込ま
ないでください。接頭辞は `+session-reserved-key-prefix+` として公開されて
おり、`(session-reserved-key-p key)` で判定できます。現在使われているのは
次の2つです。

| キー | 内容 |
|---|---|
| `"clails.current-user"` | ログイン中の利用者(第8節) |
| `"clails.csrf-token"` | このセッションの CSRF トークン(第9節) |

したがってテンプレートから `(current-session)` を走査して中身を表示しては
**いけません**。枠組み自身の項目が同じハッシュテーブルに入っており、CSRF
トークンもその1つです。アプリケーションが書いたキーを名指しで読んでください。

それ以外のキーはすべてアプリケーションのものです。枠組みの項目を残したまま
セッションを空にしたいときは
`(session-clear controller :keep-reserved t)` を使ってください。

なお、失効判定の基準となる **最終アクセス時刻は予約キーではありません**。
セッションの値の中ではなくストア側に置かれているため(第5節)、ハッシュ
テーブルを走査しても現れません。

## 4. セッションのライフサイクル API

読み書きは `gethash` で行いますが、それ以外の操作は関数として提供されます。
いずれもコントローラを渡します(要求環境のプロパティリストも渡せます)。
`clails/controller/base-controller` から再公開されているので、生成された
コントローラではパッケージ修飾なしで呼べます。

| 呼び出し | 内容 |
|---|---|
| `(session-id controller)` | 現在のセッション ID |
| `(session-new-p controller)` | このリクエストがセッションを作ったか |
| `(session-value controller key &optional default)` | 1つのキーを既定値付きで読む |
| `(session-delete controller key)` | 1つのキーを忘れる |
| `(session-clear controller &key keep-reserved)` | セッション自体は残して全キーを忘れる |
| `(session-destroy controller)` | セッションを終わらせる(ストアから削除し Cookie を失効させる) |
| `(session-regenerate-id controller)` | 内容を保ったまま ID を振り直す |
| `(session-destroyed-p controller)` | このリクエストで `session-destroy` が呼ばれたか |
| `(session-id-changing-p controller)` | この応答で ID が変わるか |

このうち2つには注意書きがあります。

- **`session-regenerate-id` はセッション固定化攻撃への対策です。** 利用者の
  権限が変わった直後(ログイン成功後、ロールの昇格後)に呼んでください。
  事前にブラウザへ植え付けられた ID が、権限を持つセッションの ID に
  ならないようにするためです。
- **`session-destroy` は明示的なログアウト用です。** 内容は即座に消え、
  応答には Cookie を失効させる `Set-Cookie` が付きます。呼び出し後に
  セッションへ書いた内容は失われるので、応答を先に組み立て、破棄は最後に
  行ってください。

## 5. 有効期限と掃除

### 寿命ではなく「放置時間」

セッションは `*session-idle-timeout*` 秒(既定 30 分)**使われなかった**
ときに失効します。生きたセッションを伴うリクエストは毎回その期限を先へ
押し出すので、作業を続けている利用者が勝手にログアウトすることはありません。
`NIL` にするとサーバ側の失効は完全に無効になり、セッションは破棄されるか
ストアが失うまで残ります。

最終アクセス時刻は **ストアが** 持ちます。セッションの値の中には入れません。
これが方針を成り立たせている点です。もしハッシュテーブルのキーにすると、
1回のページ読み込みが並行して投げる静的ファイルの取得まで含めて、
**すべてのリクエストがセッションの書き込み側に回ってしまいます**。
ストア側に置けば、時刻だけを更新する操作(インメモリなら索引の1エントリ、
DB なら1列)で済みます。

これは `updated_at` の流用でもありません。DB ストアは専用の列を持ち、
保存時と時刻更新時の両方で書きます。他の仕組みが管理する列は「読むだけの
リクエスト」では書かれないため、放置時間方式のもとでは、まさに今ページを
見ている利用者を失効させてしまいます。

### 二重の掃除

- **アクセス時の遅延削除。** 失効判定は毎リクエスト、保存された時刻から
  行われます。したがって掃除の進み具合に関係なく、失効したセッションが
  有効として扱われることは **ありません**。
- **定期掃除スレッド。** 起動時フックで開始し、停止時フックで止めます。
  `*session-sweep-interval*` 秒ごとに生きている ID を走査し、期限を過ぎた
  ものを削除します。これがないと「誰も戻ってこないセッション」が永久に
  解放されません。

サーバの停止は現在の間隔の経過を待ちません。間隔を長くしても停止が遅く
なることはありません。

### 強制終了ではフックが走らない

`SIGKILL`、電源断、クラッシュではフックが走らずにプロセスが消えます。
これは「対処」ではなく「織り込み済み」です。

- インメモリストアならセッションはプロセスと一緒に消えるので、掃除対象は
  残りません。
- 永続ストアでは行が残りますが、次のプロセスの定期掃除か、その ID が提示
  されたときの遅延削除で消えます。永久に溜まることはなく、失効済みの
  セッションが有効になることもありません。

### 定期掃除をジョブキューにしなかった理由

clails にはジョブキューがあり、「5 分ごとに何かを実行する」はジョブのように
見えます。しかし次の3点のいずれもが単独で致命的です。

1. **ワーカは別プロセス。** ジョブは Web サーバの外で動く `clails job:work`
   が取り出しますが、既定のストアはサーバプロセスのメモリにセッションを
   置いています。
2. **繰り返しの予定表がない。** キューは指定時刻以降に1回実行するだけで、
   「N 秒ごと」の概念がありません。ジョブ自身が再登録する形になり、1度
   登録に失敗すると掃除が永久に止まります。
3. **DB のテーブルが必要。** セッションの失効は、DB を持たない既定構成でも
   動かなければなりません。

## 6. ストア

`*session-store*` には、clails の
`clails/middleware/session/store:<session-store>` を継承したクラスの
インスタンスか、lack のセッションストア構造体のどちらも渡せます。段から見た
扱いは同じですが、ストアプロトコルの第4の操作(`touch-session`、最終
アクセス時刻の記録)を実装できるのは clails 側の派生だけです。lack の構造体は
CLOS クラスを継承できないため最終アクセス時刻を持てず、放置時間による失効も
働きません。

### インメモリ(既定)

`NIL` のときはスタック組み立て時にインメモリストアが作られます。開発や単一
プロセスには適していますが、プロセスを止めるとセッションは失われ、2つ目の
プロセスとは共有されません。

### データベース(本番の推奨構成)

再起動後もセッションが残り、同じテーブルを読むすべてのプロセスで共有され
ます。

```common-lisp
(setf clails/middleware/session-middleware:*session-store*
      (clails/middleware/session/store/db:make-db-session-store))
```

このストアは操作ごとに専用の接続を借りて返します。セッションの段は
トランザクションの段より **外側** にあるため、リクエストの接続で書くと
セッションの書き込みがアプリケーションのトランザクションに巻き込まれ、
ロールバックで黙って巻き戻ってしまいます。

**DB に保存するセッションには、印字して読み戻せる値しか入れられません**
(文字列、数、シンボル、リスト、ベクタ、それらのハッシュテーブル)。
クラスのインスタンスやストリームは保存できず、読み戻せない文字列を書く
代わりにエラーになります(インメモリストアにはこの制約はありません。
第8節の `current-user` も参照)。

#### テーブルを作る

```bash
clails db:create-session-table
```

- **定義体はプロジェクトの `db/session-table.lisp`** で、`clails new` が
  写します。内容を確認・編集できます。ストアも同じファイルから列名を読む
  ので、列名を変えれば両側が一緒に動きます。このファイルができる前に作られた
  プロジェクトでは、同じ内容のフレームワーク側の定義が使われます。
- **これはマイグレーションではありません。** ファイルはデータであり、読まれる
  だけで評価されません。テーブルはマイグレーション履歴にも `db/schema.lisp`
  にも現れず、`clails db:migrate` や `clails db:status` は作成も変更も
  しません。セッションテーブルはアプリケーションのスキーマではなく枠組みの
  管理情報だからです。
- **1段階で、2回実行しても安全です。** コマンドは
  `CREATE TABLE IF NOT EXISTS` を1文組み立てて実行します。2回目は何もせず、
  既にあるセッションもそのまま残ります。あとから適用する中間ファイルは
  ありません。
- **方言差は文の組み立て時に解決されます。** 同じ定義ファイルで SQLite3・
  MySQL・PostgreSQL に対応します(`datetime` と `timestamp` の綴りの違いなど)。
- **テーブルを削除するコマンドは意図的にありません。** テーブルにアプリ
  ケーションのデータは入っておらず、打ち間違いで全利用者がログアウトする
  ようなコマンドは置きません。削除が必要なら DB 側で `DROP TABLE` して
  ください。

生成されたプロジェクトでは `make db.create-session-table` が用意され、
README の「Setup Database」にも手順が載っています。

### 別のストアを作る

`<session-store>` を継承し、`fetch-session`・`store-session`・
`remove-session`(媒体が「取得→変更→保存」より良い手段を持つなら
`touch-session` も)を実装して `*session-store*` に入れてください。基底
クラスに `touch-session` の既定実装があるので、実装しなくても放置時間による
失効は働きます。

## 7. 同一セッションへの並行要求

### 枠組みが保証すること

1回のページ読み込みは同じセッション Cookie を持つ複数のリクエストに分かれる
ため、同一セッションへの並行アクセスは例外ではなく通常の状態です。そこで
セッションの段は、設定されたストアを包んで同一セッションへのアクセスを
直列化します。これにより **セッションの入れ物が壊れることはなくなります**
(テーブルの消失も、書きかけの値も起きません)。

### 保証しないこと

1回の読みと1回の書きをそれぞれ直列化しても、**その並び全体は原子的になり
ません**。2つのリクエストが同じ値を読み、変えて書き戻すと、片方の変更だけが
残ることがあります。これは欠陥ではなく仕様です。Rails や Django も同じ立場
です。

もう一方の案、すなわち **リクエスト全体でロックを保持する方式は検討のうえ
採っていません**。同じ利用者の複数のリクエストが互いの終了を待って並ぶことに
なり、しかも守る対象であるインメモリストアはそもそも本番構成ではありません。
そこを超える規模になったら共有ストアと複数プロセスへ移ることになり、1つの
イメージ内のリクエスト単位のロックはそこでは役に立ちません。

必要な場所では `with-session-lock` で並び全体を原子的にしてください。

```common-lisp
(with-session-lock (controller)
  (let ((count (or (gethash "count" (session controller)) 0)))
    (setf (gethash "count" (session controller)) (1+ count))))
```

「セッションを読んでから、読んだ値に基づいて書く」操作(カウンタの増加、
配列への追記、条件付き更新)では必ず使ってください。注意点は3つです。

- **本体は短く保つこと。** **同じ** セッションの他のリクエストは本体の終了を
  待ちます。問い合わせや外部 HTTP 呼び出しはロックの外に出してください。
  他のセッションのリクエストには一切影響しません。
- **入れ子は安全です。** ロックは再入可能です。
- **このプロセス内のロックです。** 下記を参照してください。

### 複数プロセス構成: 後勝ち

DB(将来の Redis)ストアを複数プロセスで共有する場合、**別のプロセス** が
処理する同一セッションへの並行要求では、書き戻しの片方が失われることが
あります。セッションの値は丸ごと書かれるため、後の書き込みが前の書き込みを
置き換えます。これは欠陥ではなく文書化された挙動で(ここも Rails や Django と
同じ立場です)、clails は楽観ロックや CAS を意図的に入れません。

- 既定構成である単一プロセスでは顕在化しません。
- **`with-session-lock` はここでは効きません。** 1つのイメージ内のロック
  であり、他プロセスのことは何も知りません。

## 8. `current-user`: 認証の仕組みではなく拡張ポイント

`current-user` は `session` の上に作られた薄いアクセサの対です。

```common-lisp
(current-user controller)              ; => 最後に保存した値、または NIL
(setf (current-user controller) user)  ; ログイン中の利用者として保存
(setf (current-user controller) nil)   ; 「ログアウト」
```

内部では `session` が返すのと同じハッシュテーブルの予約キー
(`"clails.current-user"`)を読み書きするだけです。別の保存領域もユーザー
モデルの要件もありません。`user` にはアプリケーションに都合のよいものを
置けます: `:id`/`:name` のプロパティリスト、毎リクエスト引き直す整数の ID、
モデルのインスタンスなど。

**DB セッションストアを使う場合の注意:** ここに置いた値はセッションの値の
一部になるため、印字して読み戻せる必要があります(第6節)。プロパティリスト
や ID は条件を満たしますが、モデルのインスタンスは満たしません。ID を保存して
毎リクエスト引き直すのが移植性のある選択です。

### ログイン/ログアウトの例(説明用)

**この例は意図的に最小限で、本番のセキュリティ水準ではありません。** API の
形を示すためのもので、パスワードのハッシュ化、時間差の出ない比較、流量制限は
いずれも行っていません。これらは自分で実装するか、専用のライブラリを使って
ください。

```common-lisp
(defclass <session-controller> (<rest-controller>)
  ())

;; POST /login  { "email": "...", "password": "..." }
(defmethod do-post ((controller <session-controller>))
  (let* ((email (param controller "email"))
         (password (param controller "password"))
         ;; find-user-by-email / verify-password はプロジェクト側のコード。
         ;; clails はユーザー検索もパスワード検証も提供しない。
         (user (find-user-by-email email)))
    (if (and user (verify-password user password))
        (progn
          ;; 権限が変わったので ID を振り直す(第4節)
          (session-regenerate-id controller)
          (setf (current-user controller) (list :id (ref user :id)
                                                :email (ref user :email)))
          (set-response controller '((:status . "ok"))))
        (progn
          (setf (slot-value controller 'code) 401)
          (set-response controller '((:status . "error")
                                     (:message . "invalid credentials")))))))

;; DELETE /login (ログアウト)
(defmethod do-delete ((controller <session-controller>))
  (set-response controller '((:status . "ok")))
  (session-destroy controller))
```

ログイン必須のコントローラは次のように書けます。

```common-lisp
(defclass <account-controller> (<web-controller>)
  ())

(defmethod do-get ((controller <account-controller>))
  (let ((user (current-user controller)))
    (if user
        (set-view controller "account/show.html" `(:user ,user))
        (set-redirect controller "/login"))))
```

この判定は素の Lisp なので、ヘルパー関数や `:before` メソッドに切り出す
などプロジェクトの作法に合わせて自由に整理できます。clails は特定の認可
パターンを強制しません。

## 9. CSRF 対策

### 9.1 この段がすること

`*enable-csrf-middleware*` を `T` にすると、**状態を変える要求**(POST・PUT・
PATCH・DELETE)はすべて、このセッションのトークンを伴わなければなりません。
トークンが無い要求や一致しない要求には **403** を返し(本文は
`*csrf-forbidden-message*`)、拒否は操作種別・道筋・接続元アドレスとともに
`:audit` の口に記録されます。GET と HEAD は検証しません。

トークンはセッション単位で、必要になった時点で作られます。最初にトークンを
求めたテンプレートがセッションに1つ置き、以後そのセッションのどのページの
どのフォームも同じトークンを共有します。

知っておく価値のある3点:

- **解釈できない本文は例外ではなく 403 になります。** 壊れた JSON、最上位が
  配列の JSON、空の本文、宣言された `Content-Type` と食い違う本文 — いずれも
  同じ 403 で拒否され、解析エラーがミドルウェアスタックの外へ抜けることは
  ありません。
- **照合は長さに依存せず、途中で打ち切りません。** かかった時間から「推測した
  トークンのうちどこまでが当たっていたか」が漏れないようにするためです。
- **セッションの段も有効でなければなりません。** トークンはセッションの中に
  あるためです。セッション無効のまま CSRF を有効にした構成は状態変更要求を
  1件も処理できないので、スタックの組み立て時に拒否されます
  ([11. 構成の整合検査](#11-構成の整合検査strict))。

位置: **セッションの段より内側**(トークンがセッションにあるため)、
**振り分けの段より外側**(アクションに届く前に拒否しなければならないため)。
スタック全体は [環境設定ガイド](environment_ja.md) を参照してください。

### 9.2 フォームにトークンを入れる

隠し欄を自分で書かず、フォームヘルパを呼んでください。ヘルパは
`clails/view/form-helper` にあり、生成されるビューの名前空間 —
`app/views/package.lisp` と、`clails generate:view` が書く
`app/views/<リソース>/package.lisp` — は既にこれらを取り込んでいるので、
テンプレートからは修飾なしで呼べます。

```html
<%= (form-tag :url "/todos" :method :post) %>
  <input type="text" name="title">
  <input type="submit" value="作成">
<%= (end-form-tag) %>
```

これで `<form>` の開始タグと隠しのトークン欄が出力されます。更新・削除では
意図する操作種別を渡せば、隠しの `_method` 欄も一緒に出ます(第10節)。

```html
<%= (form-tag :url (format nil "/todos/~A" (view :id)) :method :put) %>
  <input type="text" name="title" value="<%= (view :title) %>">
  <input type="submit" value="保存">
<%= (end-form-tag) %>

<%= (form-with :url (format nil "/todos/~A" (view :id))
               :method :delete
               :body "<input type=\"submit\" value=\"削除\">") %>
```

**ヘルパへの到達方法は2通りあります。** 1つはビューの名前空間に取り込む方法
で、生成されるプロジェクトはこちらです。

```common-lisp
(defpackage #:myapp/views/todo/package
  (:use #:cl)
  (:import-from #:clails/view/view-helper
                #:*view-context*
                #:view)
  (:import-from #:clails/view/form-helper
                #:form-tag
                #:end-form-tag
                #:form-with
                #:form-authenticity-token
                #:csrf-token-tag
                #:method-override-tag))
```

もう1つは **何も取り込まず**、テンプレートに
`clails/view/form-helper:form-tag` と完全修飾で書く方法です。どちらでも動き、
取り込みは利便性のためのものです。

**各ヘルパの働き:**

| 呼び出し | 結果 |
|---|---|
| `(form-tag :url u :method m :multipart b :attributes plist)` | `<form>` の開始タグと必要な隠し欄。`:url` が `NIL` なら `action` を書かない(＝現在の URL に送信)。`:method` は `:get :post :put :patch :delete` のいずれか。`:multipart` が `T` なら `enctype="multipart/form-data"` を付ける。`:attributes` は `<form>` に足す属性のプロパティリスト(例: `(:class "edit")`) |
| `(end-form-tag)` | `"</form>"` |
| `(form-with :url … :method … :multipart … :attributes … :body b)` | `form-tag`・`BODY`・`end-form-tag` を1つの式で。`:body` は文字列、文字列のリスト(順に連結)、または `NIL`(空のフォーム) |
| `(form-authenticity-token)` | トークンそのものの文字列。検証が無効なら `NIL` |
| `(csrf-token-tag)` | 隠しのトークン欄だけ。検証が無効なら `""` |
| `(method-override-tag :put)` | 隠しの `_method` 欄だけ。`:get` と `:post` では `""` |

**動く条件と、動かないときに何が起こるか。** これらはテンプレート用です。
理由は2つあり、それぞれ別です。セッションは描画中のコントローラから得られ、
その束縛はテンプレートの実行中だけ存在します。トークンは CSRF の段が1リクエ
ストの間だけ束縛する動的変数から得られます。したがって:

- 検証が **無効** のとき、`(csrf-token-tag)` は `""`、
  `(form-authenticity-token)` は `NIL` を返します。CSRF を有効にしていない
  プロジェクトでテンプレートが壊れないようにするためです。
- **テンプレートの外** から呼ぶと、どのヘルパかを名指しした
  `view-context-error` になります。
- `*enable-csrf-middleware*` が `T` なのに **CSRF の段を通らないスタック**
  で描画されたテンプレートから呼ぶと、そのことを述べる
  `form-helper-error` になります(下位ライブラリ内部の
  `unbound-variable` が外に出てくるのではありません)。

**GET のフォームにはトークンを入れません(意図的)。** `form-tag` は
`:method :get` のときトークン欄を出しません。GET のフォームの項目は URL の
問い合わせ文字列として付くため、トークンがブラウザの履歴、次のページから
辿ったリンクの `Referer` ヘッダ、そして経路上のすべてのアクセスログに残って
しまいます。そもそも CSRF の段は GET を検証しないので、失うものはありません。

同じ理由で、`_method` 欄はフォームの **本文** に書かれ、送信先 URL の
問い合わせ文字列には決して入りません。問い合わせ文字列に操作種別を書けると、
ただのリンクが削除に化けてしまいます。

### 9.3 トークンの送信方法

| 場所 | 受け付けるか |
|---|---|
| **本文の最上位の項目**(`*csrf-form-token*` = `"_csrf_token"`) | **受け付ける** — 通常の経路で、`form-tag` が出力するもの。`multipart/form-data` でも同じ(隠し欄が独立したパートになる) |
| **`X-CSRF-Token` ヘッダ**(`*csrf-header-name*`。大小文字は区別しない) | **受け付ける** — 本文を自由にできない `fetch`/XHR の呼び出し向け |
| **問い合わせ文字列** | **受け付けない。** ログ・プロキシの履歴・`Referer` ヘッダに残る |
| **JSON の入れ子の中**(`{"meta": {"_csrf_token": "…"}}`) | **受け付けない。** 段の判定がアプリ側の JSON の形に依存してはならない |
| **文字列でない値**(`{"_csrf_token": 12345}`) | **受け付けない。** 比較するのは文字列だけ |

本文の項目とヘッダの両方を伴う要求では、**本文の項目が勝ちます**。トークンを
置く場所として明示的で目に見えるのは本文の項目であり、ヘッダが上書きできると
経路上のどこかで注入されたヘッダが判定を決めてしまうためです。

### 9.4 使い切り方式を選ぶ場合の代償

`*csrf-one-time-token*` の既定は `NIL` で、トークンをセッションの間
**使い回します**。`T` にすると使い切りになり、検証に成功した要求がセッション
からトークンを取り除くので、再送は拒否されます。**既定ではなく、明示的に選ぶ
設定です。** 以下のように、踏みやすい形で使いやすさを損なうためです。

1. **再送は常に拒否されます。** 戻るボタンを押してからの再送信、送信ボタンの
   二度押し、通信失敗後の素朴な再試行がいずれも失敗します。
2. **1ページ上の全フォームが同一トークンを共有する** ため、どれか1つを送信
   すると画面に残っている他のフォームはすべて無効になります。**行ごとに操作
   フォームを置く一覧画面で最も影響が大きく**、1行のボタンを押すと他の行の
   ボタンは再読み込みまで死にます。
3. **複数タブを開くこと自体は安全です** — ページを開くだけでは他のタブの
   フォームは無効になりません(2度描画しても同じトークンが返るため)。
   **ただし、どれか1つのタブが送信した瞬間に他のタブのフォームは無効に
   なります。**
4. **並行する非同期送信はちょうど1本だけが成功します。** 並行送信を行う
   アプリケーションは「残りは拒否される」前提で書く必要があります。
5. **成功した要求のアクション本体からはトークンを読めません**(すでに消費
   済みのため)。用紙を再描画すれば新しいトークンが作られるので、
   「送信 → 再描画」は自己修復します。
6. **セッションが失効したり識別子が入れ替わるとトークンも失われます。**
   そのまま開いていた用紙は、送信前に再読み込みが必要になります。
7. **利用者に「再読み込みしてやり直す」ことを伝える必要があります。**
   `*csrf-forbidden-message*` の既定文はそう書いてありますが、403 の本文は
   それを置く良い場所ではありません。使い切りでは正当な利用者が拒否される
   頻度が十分に高いので、アプリケーション側で扱うべきです。
8. **向くのは「単一フォーム・非同期なし・再試行なし」の画面です。** 行ごとに
   フォームを置く一覧画面、複数のフォームがあるページ、並行送信する
   JavaScript クライアント、再試行する仕組みには向きません。
9. **代償にならないこと**(いずれも実測済みで回帰テストあり): 検証に
   **失敗** してもトークンは消費されないので、第三者が無効なトークンを投げ
   つけて利用者のトークンを壊すことはできません。また同じ用紙を2度描画しても
   同じトークンが返ります。

### 9.5 トークンの置き場所

`*csrf-session-key*` の指すキーで、既定は `"clails.csrf-token"` — 予約キー
(第3節)です。下位ライブラリ自身の既定名には接頭辞が無く、アプリケーションが
同名の値をセッションに置くと枠組みのトークンと黙って衝突しうるためです。

### 9.6 検証の免除は提供しません(その代償)

**このゴールでは CSRF 検証の免除を提供しません。** 道筋単位でも、コントローラ
やアクション単位でもです。`*enable-csrf-middleware*` を `T` にすると、
**すべてのエンドポイント** が検証対象になります。

これには実際の帰結が1つあります。**第三者が呼ぶ経路 — Webhook、決済事業者の
コールバック、POST で叩く死活監視 — を受けたい場合、現状の選択肢は
「CSRF をアプリケーション全体で無効にする」しかありません。**

```common-lisp
;; 今日 Webhook を受けるための唯一の方法。下の警告を先に読んでください。
(setf clails/middleware/csrf-middleware:*enable-csrf-middleware* nil)
```

**安易に採らないでください。** 全体で無効にすると、用紙経由の経路も含めて
**すべての** 経路から保護が外れます。アプリケーション全体がサイト間要求に
対して開くことになり、それはまさにこの段が止めるための攻撃です。免除が入る
前にどうしても Webhook を受けなければならない場合、比較的安全な形は
「その経路だけ CSRF を無効にした別アプリケーション(別プロセス)に置く」か、
「CSRF は有効のままにして、第三者には状態を変えない操作種別を呼ばせる」
です。

**免除は後続のゴールで提供予定** で、順序も決まっています。

1. **道筋(パス)単位。** 段の入口で道筋を照合して素通しするだけで済み、
   いまの形にそのまま乗ります。
2. **コントローラ／アクション単位。** こちらは難しく、手間の問題ではあり
   ません。**CSRF の段ではコントローラが未決定** だからです。コントローラ
   単位で検証するには検証を経路解決のあとに移すことになり、`_method` の
   偽装を安全にしている段の順序(検証 → 読み替え → 振り分け。第10節)と
   衝突します。`_method=GET` の抜け道を復活させずにその順序を作り直す必要が
   あるため、こちらが後になります。

## 10. 操作種別の読み替え(`_method`)

HTML の `<form>` は GET と POST でしか送信できません。リソースの更新・削除の
経路は PUT・PATCH・DELETE で到達するため、それらを意図するフォームは隠しの
`_method` 欄でそう宣言し、この段が **経路照合の前に、宣言された操作種別を
書き換えます**。

この書き換えが、`_method` を新方式(`:action` ベースのルーティング)でも
使えるようにしているものです。経路照合はリクエスト環境から操作種別を読み、
その値こそこの段が書き換えるものなので、経路照合も従来の
`do-get`/`do-post`/`do-put`/`do-delete` 振り分けも、どちらも用紙が意図した
操作種別を見ます。

**この段は既定で有効です**(枠組みの `*enable-method-override*` は `T`)。
セッションと CSRF の段とは異なります。あの2つは **すべての** 要求への応答の
仕方を変えますが、この段は要求自身が欄を伴うときだけその要求を変え、しかも
行うのはその欄の文書化された目的そのものです。

### 10.1 安全上の前提

これらは実装の詳細ではなく性質であり、どれを回避しても穴が開きます。

- **POST だけを書き換えます。** GET には一切触りません。
- **PUT・PATCH・DELETE にだけ** 書き換えます — 許可値の明示的な一覧(これが
  全部)で、実行時に増えることはありません。特に `GET`・`HEAD`・`OPTIONS` は
  偽装できません。それらは CSRF 検証の対象外なので、偽装できればトークン
  無しで処理させる手段になってしまいます。
- **値は要求の本文からのみ読み**、問い合わせ文字列からは読みません。
  問い合わせ文字列に操作種別を書けると、ただのリンク(や画像タグ)が削除に
  化けます。
- **未知の値では操作種別を変えません。** `_method=banana` はエラーではなく
  POST のままです。
- **この段は CSRF 検証の内側で動きます。** 外側に置くと、安全な操作種別に
  書き換えられた POST が未検証で通ってしまいます(`_method=GET` ＋ トークン
  無しの抜け道)。段の順序(CSRF → 読み替え → 振り分け)がそれを閉じており、
  順序が崩れた構成は整合検査が捕らえる2つの構成のうちの1つです(第11節)。

### 10.2 既存プロジェクトで変わること

- **同じ道筋に POST の経路と PUT / PATCH / DELETE の経路を両方書いている
  手書きの経路表は挙動が変わります。** `_method=put` を伴う POST は、以前は
  経路照合が実際の操作種別を見ていたため **POST の経路** に届いていましたが、
  いまは **PUT の経路** に届きます。これは意図した効果 — 用紙が更新の経路に
  到達できるようにするもの — ですが、その形の経路表で従来の挙動に依存して
  いた場合は、2つの経路の道筋を分けるか、`*enable-method-override*` を
  `NIL` にしてください。
- **`(resources …)` で作った経路表は影響を受けません。** 同じ道筋に同じ
  操作種別を宣言する項目が2つ存在しないためです。
- **`(resources …)` は 7 件ではなく 8 件の経路を生成するようになりました。**
  `update` アクションの 2 件目として PATCH が加わっています。CSRF 検証は
  以前から状態変更の 4 操作すべてを対象にしており、読み替えも PUT / PATCH /
  DELETE の 3 つを受け付けるので、PATCH の経路が無いリソースでは
  「検証されるのに到達できない操作種別」が1つ残っていました。両方の項目が
  `:update` という名前なので、`:only '(:update)` は両方を残し、
  `:except '(:update)` は両方を外します。
  [コントローラガイド](controller_ja.md#resources-関数による-restful-ルーティング)
  を参照してください。

## 11. 構成の整合検査(strict)

`clails/environment:*strict-configuration*` は、**動きえない構成** を
clails が見つけたときに何をするかを決めます。

| 値 | 検査が失敗したとき |
|---|---|
| `T`(フレームワーク既定) | **中止。** 起動時の検査はエラーを発します(したがってミドルウェアスタックは組み立てられません)。リクエスト単位の検査は **403** を返します |
| `NIL` | **警告して続行。** 同じ検査が `:audit` の口に警告を記録し、処理は続きます |

**環境ごとの値:** フレームワークの既定は `T`、生成されるプロジェクトは
`app/config/environment.lisp` の `setup-environment/<環境>` 関数で
**開発と試験では `NIL`、本番では `T`** を入れます。**clails は実行中の環境を
判定しません** — この変数だけを読みます。だからこそ環境差はプロジェクトの
設定ファイルが担います。Cookie の Secure とまったく同じ原則です。

### 11.1 検査される2つの構成

1. **セッション無効のまま CSRF を有効にした構成。** ミドルウェアスタックの
   組み立て中に1度だけ検査されます。この構成は 100% 動きません — トークンは
   セッションの中にあるので、状態変更要求が1件も成功しません — それが `T` を
   安全な既定にしている理由です。誤検出の余地がありません。
2. **段の配置が崩れた構成**、すなわち読み替えの段が CSRF 検証より **外側**
   にある構成。リクエストごとに、CSRF の段が通した要求に残すマーカーを探して
   検査します。`T` なら 403 で拒否し、`NIL` なら **読み替えなしで** 処理
   します。

### 11.2 非 strict は「穴が開いたまま動く」ということ

ここは2度読む価値があります。`*strict-configuration*` が `NIL` で段の配置が
崩れていると、**何もエラーになりません。** 要求は処理され、`_method=GET` の
抜け道が静かに開きます — POST が安全な操作種別を宣言してトークン無しで処理
されうる、ということです。手がかりは警告だけで、しかも

- **警告は `:audit` の口に出ます。** 枠組み内部向けのパッケージロガーでは
  ありません。あちらは生成プロジェクトの開発・試験で水準が `:error` なので、
  警告がまったく表示されないからです。
- **段の配置の警告はプロセスごとに1回だけ出ます。** リクエストごとに出して
  ログを溢れさせないためですが、同時にこれが見逃しやすい理由でもあります。
  起動直後に1行出て、あとは二度と出ません。

したがって開発環境では、スタックを変えたあとに監査の記録を読んでください。

### 11.3 検査の影響を受けないもの

- **`clails task` と `clails console` はミドルウェアスタックを組み立てない**
  ため、どちらの検査も走らず、この設定の影響を受けません。
- **段を包むことと、段の列を丸ごと置き換えることは誤検出になりません。**
  配置の検査はミドルウェアの列を走査するのではなく、要求に残されたマーカー
  —— 実際にその要求が通った順序 —— を見ます。だからこそ、文書自身が示して
  いる2つの形(段を包む、列を組み直す)で誤検出しません。
- **ただし CSRF の段を外したまま読み替えの段を残した構成では検査が発火
  します。** それが狙いです。穴が開いているのはまさにその構成です。

## 12. 既存プロジェクトの移行手順

`clails new` はプロジェクトの設定を **1度だけ** 書き出します。今回の変更が
既存のプロジェクトに及ぶことはないので、以下はすべて手作業で、すべて任意
です(何も変えなければセッション無効のまま従来どおり動きます)。

1. **セッションと CSRF の設定を追記する。** `app/config/environment.lisp` に
   追記します。使い捨てのプロジェクトを生成し(`clails new scratch`)、その
   `app/config/environment.lisp` から「Sessions」「CSRF protection」
   「Request-method override」と環境ごとの塊を、
   `setup-environment/<環境>` 関数ごとコピーするのが簡単です。
2. **環境ごとの部分を boot から呼ぶ。** Secure と `*strict-configuration*`
   はどちらもミドルウェアスタックの組み立て時に読まれ、これは最初の起動時
   フックより **前** に起こるため、起動時フックでは間に合いません。生成
   される `clails.boot` では `resolve-project-environment` の直後に
   `(<プロジェクト>/config/environment:initialize-environment-config)` を
   呼んでいます。同じ行を自分の `clails.boot` に追加し、設定パッケージから
   この関数を公開してください。この手順を省くと、本番でも Cookie に Secure
   が付かず、開発でも壊れた構成が警告ではなく中止になります。
3. **`*clails-middleware-stack*` を丸ごと置き換えている場合**、その
   スタックにはセッションの段も CSRF の段も読み替えの段もないため、上記の
   設定を足しても有効になりません。自分で足す段は
   `add-middleware-before` / `add-middleware-after` で足すように変更し、
   枠組みの段を本来の位置に残してください
   ([環境設定ガイド](environment_ja.md))。なお読み替えの段を残して CSRF の
   段だけ外したスタックは `_method=GET` の穴が開いた構成そのもので、
   整合検査が拒否する対象です(第11節)。
4. **DB にセッションを置く場合**、生成したプロジェクトから
   `db/session-table.lisp` をコピーし(同じ内容の組み込み定義に任せることも
   できます)、環境ごとに `clails db:create-session-table` を実行して
   `*session-store*` に `(make-db-session-store)` を設定します。make の
   近道が欲しければ `db.create-session-table` ターゲットを自分の `Makefile`
   に足してください。生成される `Makefile` と `README.md` も一度しか写され
   ないため、既存プロジェクトには及びません。
5. **Cookie の既定が変わっていることに注意してください。** 以前のセッション
   は引き継がれません。Cookie 名が下位ライブラリの `lack.session` ではなく
   なったため、古い Cookie を持つブラウザは1度だけ新しいセッションを始めます
   (つまりログイン中の利用者は1度ログアウトされます)。新しい Cookie は
   HttpOnly で `SameSite=Lax` を明示し(サイト間の POST には送られなくなり
   ます)、失効日時を持ちません。従来の挙動に揃えたい場合は、自分で状態を
   組み立てて `:cookie-key "lack.session"` を渡してください(第2節)。
6. **本番の記録設定の誤りを直しました。** 生成される
   `app/config/logger.lisp` で、往復記録用の口が `:sql` という名前で登録され
   ていたため、`:web-access` が未登録になり、SQL の記録が
   `logs/access.log` に行って `logs/sql.log` が空のままになっていました。
   修正はテンプレート側なので既存プロジェクトには及びません。自分の
   `setup-logger/production` を新しく生成したものと見比べ、`:sql`・
   `:web-access`・`:audit`・`:task` がそれぞれ1回だけ登録されていることを
   確認してください。これは記録だけの問題ではありません。拒否した要求と
   第11節の構成警告を記録するのは `:audit` の口です。
   同じテンプレートで是正した点がさらに2つあります。`:job` を3環境すべてで
   登録するようにしました(`clails/logger:log.job` は `:info` で書くため、
   `:job` が未登録だと開発では全体の既定に混ざり、試験と本番では捨てられて
   いました)。また本番の `:sql` の登録から宛先ファイルを外しました — 本番は
   debug を出さず `log.sql` は `:debug` 固定なので、あのファイルは一度も
   書かれえませんでした。
7. **操作種別の読み替えの段は既定で有効** なので、設定は要りません。ただし
   **同じ道筋に POST の経路と PUT / PATCH / DELETE の経路を両方書いている
   手書きの経路表は挙動が変わります**。`_method=put` を伴う POST が PUT の
   経路に届くようになります。`(resources …)` で作った経路表は影響を受け
   ません。その形の経路表で従来の挙動に依存していた場合は、2つの経路の
   道筋を分けるか `*enable-method-override*` を `NIL` にしてください
   ([10.2](#102-既存プロジェクトで変わること))。
8. **ビューの名前空間にフォームヘルパを追加する。** 生成されるプロジェクト
   は `app/views/package.lisp` と各 `app/views/<リソース>/package.lisp` で
   `clails/view/form-helper` から `form-tag`・`end-form-tag`・`form-with`・
   `form-authenticity-token`・`csrf-token-tag`・`method-override-tag` を
   取り込みます。これらのファイルも一度しか写されないため、既存プロジェクト
   では自分で `:import-from` を足す必要があります。あるいは取り込まずに
   テンプレートで `clails/view/form-helper:form-tag` と完全修飾で書いても
   かまいません([9.2](#92-フォームにトークンを入れる))。
9. **フォームの手書きの隠し欄を置き換える。** 検証を有効にすると、手で
   書いた `<form method="POST">` はトークンを伴うまですべて 403 になります。
   `form-tag` / `form-with` が `_method` 欄と一緒にトークン欄を書きます。
   あわせて、**ビューを設定しないアクションが 200 ＋ 空の本体を返すように
   なった** ことにも注意してください(以前は失敗していました)。そのような
   アクションに送信する用紙は「成功したように見える」ので、応答コードでは
   なくアクションを確認してください。

## まとめ

1. 生成されたプロジェクトではセッションは **有効**、フレームワークの既定は
   **無効** です。したがって既存プロジェクトは設定を足すまで影響を受けません。
2. `(session controller)` はリクエストスコープの Cookie 連動ハッシュテーブル
   です。`clails.` で始まるキーは枠組みの予約です。
3. セッションは既定で **30 分の放置** で失効し、遅延削除と定期掃除の両方で
   削除されます。Cookie は設計上、失効日時を持ちません。
4. Cookie は HttpOnly・`SameSite=Lax` で、実装を推測されない名前を使います。
   **Secure は既定で無効で、プロジェクトの設定が環境ごとに有効化します** —
   本番では有効、平文の開発では無効です。
5. 既定はインメモリストア、本番の推奨は DB ストアで、そのテーブルは
   `clails db:create-session-table` で1度だけ作ります。
6. 並行要求でセッションが壊れることはありませんが、「読んで変えて書く」では
   更新が失われることがあります。`with-session-lock` を使ってください。
   複数プロセスでは後勝ちになります。
7. `current-user` は「ログイン中の利用者」の配線です。ログイン処理・
   パスワードの扱い・認可はプロジェクトの責任です。
8. **生成されたプロジェクトでは CSRF 検証が有効** で、フレームワークの既定は
   無効です。POST / PUT / PATCH / DELETE はすべてセッションのトークンを必要
   とし、隠し欄は `form-tag` / `form-with` が書きます。GET のフォームには
   意図的にトークンを入れません。このリリースには **経路単位の免除がない**
   ため、Webhook を受けるには CSRF を全体で無効にするしかなく、それは危険
   です。後続のゴールで対応します(まず道筋単位、次にコントローラ／
   アクション単位)。
9. **用紙からリソースの更新・削除の経路に到達できます。** 隠しの `_method`
   欄を、CSRF 検証の内側で動き、PUT / PATCH / DELETE だけを受け付け、本文の
   みを読む段が honour します。`(resources …)` は PATCH を含む 8 件の経路を
   生成するようになりました。
10. **`*strict-configuration*` はフレームワークと本番で `T`、生成プロジェクト
   の開発・試験で `NIL`** です。`NIL` では段の配置が崩れていても
   `_method=GET` の穴が開いたまま処理され、`:audit` の口にプロセスごとに
   1回だけ警告が出ます。
