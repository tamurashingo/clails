# clails Session & Authentication Guide

## Overview

clails ships a cookie session stage, built on top of
[`lack-middleware-session`](https://github.com/fukamachi/lack), plus a tiny
`current-user` extension point on top of that session.

Two defaults are worth knowing before anything else:

- **A project generated by `clails new` has sessions switched on.** The lines
  that do it are in `app/config/environment.lisp`, written out with comments,
  and `(session controller)` works from the first request.
- **The framework's own default is "off".** An existing project whose
  configuration says nothing about sessions keeps behaving exactly as it did:
  no cookie is set, and `(session controller)` signals an error telling you to
  enable the stage. Nothing in this release changes an existing project by
  itself — see [9. Migrating an existing project](#9-migrating-an-existing-project).

What clails provides, and what it does not:

- **Session support** is a real, framework-provided feature: a per-request,
  cookie-backed hash table every controller can read and write, with
  server-side expiry, cleanup, a per-session lock and a choice of stores.
- **`current-user`** is *plumbing only*. clails does **not** implement any
  authentication scheme — no password hashing, no login/logout routes, no
  "user" model convention. It gives you a documented, session-backed place to
  store "whoever is currently logged in," so that every project does not have
  to invent its own. Your project implements the login logic and calls
  `(setf (current-user controller) ...)` once it succeeds.

Explicitly **out of scope** (not provided by clails):

- Remember-me / persistent-login tokens
- OAuth / OIDC integration
- Role-based authorization or permission checks
- A bundled password-hashing helper

### A note on CSRF protection

This release does **not** switch any CSRF protection on, so a generated
project has none. That is not a step backwards: a project that enabled
sessions before this release had none either. What this release adds is the
session side of the problem — concurrent requests can no longer corrupt a
session, sessions expire and are cleaned up, and the cookie defaults moved to
the safe side. CSRF protection is the subject of the next piece of work; it is
not configured by the templates and not described in this guide yet.

## 1. Configuration

Every session setting is declared in a session-specific package and
re-exported by `clails/middleware/session-middleware` (and once more by
`clails/middleware`), so one package reaches all of them.

**All of them are read once, while the middleware stack is being built by
`clails server`.** Set them in `app/config/environment.lisp`, which is loaded
before the server starts; changing them in a running image does not change how
the running server answers.

### What a generated project contains

```common-lisp
(in-package #:myapp/config/environment)

;; Enable clails' cookie session stage.
(setf *enable-session-middleware* t)

;; NIL = clails' in-memory store (see section 6 for the database store).
(setf *session-store* nil)

;; How long a session may stay unused before it expires, in seconds.
(setf *session-idle-timeout* 1800)

;; Expired sessions are also removed by a background sweeper.
(setf *session-sweep-enabled* t)
(setf *session-sweep-interval* 300)
```

The Secure flag of the cookie is the one setting that differs per environment,
so the generated configuration puts it in a function per environment —
`setup-session/develop`, `setup-session/test`, `setup-session/production` —
and `clails.boot` calls `initialize-session-config` once `CLAILS_ENV` has been
resolved. See [2. The session cookie](#2-the-session-cookie).

### Settings reference

| Setting | Meaning | Framework default | Recommended |
|---|---|---|---|
| `*enable-session-middleware*` | Whether the session stage does anything at all | `NIL` (off) | `T` — a generated project sets it |
| `*session-store*` | Where sessions are kept; `NIL` means a fresh in-memory store | `NIL` | in-memory for development; the database store in production |
| `*session-state*` | The cookie; `NIL` means clails' own state, built with the Secure flag below | `NIL` | leave it alone unless you need another cookie name, path, domain or SameSite |
| `*session-cookie-secure*` | Mark the cookie Secure (sent over HTTPS only) | `NIL` | `T` wherever the application is served over HTTPS; `NIL` for plain-HTTP development and test |
| `*session-idle-timeout*` | Seconds a session may stay unused before it expires; `NIL` switches server-side expiry off | `1800` (30 minutes) | 1800, or shorter for sensitive applications |
| `*session-sweep-enabled*` | Whether the periodic sweeper thread runs | `T` | `T` |
| `*session-sweep-interval*` | Seconds between two sweeps | `300` (5 minutes) | 300; a longer interval only delays freeing, it never honours an expired session |

The stage is always in the middleware stack, in a fixed position — it has to
sit outside the transaction stage and the routing stage — so enabling sessions
never means editing `*clails-middleware-stack*`. When
`*enable-session-middleware*` is `NIL` the stage is a pure passthrough. See the
[Environment Guide](environment.md) for the stack as a whole.

## 2. The session cookie

The cookie clails emits by default is

```
_session_id=<40 hex characters>; path=/; HttpOnly; SameSite=Lax
```

- **HttpOnly** — no script can read the session id.
- **SameSite=Lax**, stated explicitly. Leaving the attribute out is not
  "unspecified": the response builder underneath then defaults it to `None`
  and warns on every response.
- **A name that says nothing about the implementation.** The previous default
  came from the underlying library and was called `lack.session`, which told
  anyone looking at a response which library — and therefore which
  version-specific weaknesses — to try.
- **No expiry date, deliberately.** The deadline is the server-side idle
  timeout (section 5). A date on the cookie could not express that policy: the
  stage attaches `Set-Cookie` only when the session is created, when its id
  changes and when it is destroyed, so a date on it is never refreshed and
  would become an *absolute* deadline counted from the moment the session was
  created. In the browser's terms it is therefore a session cookie: it is gone
  when the browser is closed, while the server's idle timeout is the only
  deadline that matters.

### Secure: the setting that differs per environment

`T` means the browser sends the cookie **over HTTPS only**. The framework
default is `NIL`, and that is a deliberate exception to "default to the safe
value": a Secure cookie is not sent over plain HTTP *at all*, so turning it on
in a development environment without TLS stops sessions from working
altogether — the cookie is set, never comes back, and every request looks like
a first visit.

**clails never inspects which environment it is running in.** It reads
`*session-cookie-secure*` and nothing else, which is why the environment
difference lives in the project's configuration file:

```common-lisp
(defun setup-session/develop ()
  (setf *session-cookie-secure* nil))   ; plain HTTP

(defun setup-session/test ()
  (setf *session-cookie-secure* nil))   ; plain HTTP

(defun setup-session/production ()
  (setf *session-cookie-secure* t))     ; HTTPS only
```

### Changing the cookie

```common-lisp
(setf clails/middleware/session-middleware:*session-state*
      (clails/middleware/session/state/cookie:make-clails-cookie-state
        :cookie-key "_myapp_session"
        :path "/"
        :samesite :strict))
```

A state built by hand carries its own `:secure`, so `*session-cookie-secure*`
is then no longer consulted. A lack cookie state is accepted here as well, and
is the way to ask for a *persistent* cookie (one that survives the browser
being closed), which the clails state deliberately cannot express. The
server-side idle timeout keeps applying either way.

## 3. Reading and writing session data

Every controller instance has a `session` accessor that returns a per-request
hash table (`:test 'equal`), backed by the cookie session:

```common-lisp
(defmethod do-get ((controller <my-controller>))
  (let ((visits (or (gethash "visits" (session controller)) 0)))
    (setf (gethash "visits" (session controller)) (1+ visits))
    (set-view controller "home/index.html"
              `(:visits ,(gethash "visits" (session controller))))))
```

Data placed in the hash table is committed back into the store after the
response is generated, and the client keeps (or receives) its cookie, so the
same contents are available on the next request.

If `*enable-session-middleware*` is `NIL`, `(session controller)` signals an
error telling you to enable the stage. Silently returning a throwaway hash
table would make it easy to lose data without noticing.

### Reserved keys: the `clails.` prefix

**Keys beginning with `clails.` belong to the framework.** Do not write them
from an application, and do not expect to find your own data there. The prefix
is available as `+session-reserved-key-prefix+`, and
`(session-reserved-key-p key)` answers whether a key is one of them; the one
in use today is `"clails.current-user"`.

Everything else in the hash table is yours. `(session-clear controller
:keep-reserved t)` is the way to empty a session without discarding the
framework's own entries.

Note that the last-access time a session's expiry is measured from is **not** a
reserved key: it lives in the store, not in the session value (see
section 5), so an application that walks the hash table never sees it.

## 4. The session lifecycle API

Reading and writing work through `gethash`. The operations that do not are
functions, each taking the controller (a request environment plist is accepted
too). They are re-exported by `clails/controller/base-controller`, so a
generated controller can call them unqualified:

| Call | What it does |
|---|---|
| `(session-id controller)` | The current session id |
| `(session-new-p controller)` | True when this request created the session |
| `(session-value controller key &optional default)` | Read one key, with a default |
| `(session-delete controller key)` | Forget one key |
| `(session-clear controller &key keep-reserved)` | Forget every key, keeping the session itself |
| `(session-destroy controller)` | End the session: drop it from the store and expire the cookie |
| `(session-regenerate-id controller)` | Give the session a new id, keeping its contents |
| `(session-destroyed-p controller)` | True when `session-destroy` was called for this request |
| `(session-id-changing-p controller)` | True when a new id will be minted for this response |

Two of them deserve a note:

- **`session-regenerate-id` is the defence against session fixation.** Call it
  as soon as the user's privileges change — right after a successful login, or
  after elevating a role — so that an id planted in the browser beforehand is
  not the id of the privileged session.
- **`session-destroy` is for an explicit logout.** The contents are cleared
  immediately and the response carries a `Set-Cookie` that expires the cookie.
  Anything written into the session after that call is lost, so write the
  response first and destroy last.

## 5. Expiry and cleanup

### Idle time, not lifetime

A session expires when it has been **unused** for `*session-idle-timeout*`
seconds — 30 minutes by default. Every request that carries a live session
pushes the deadline forward, so a user who keeps working is never logged out.
Setting the variable to `NIL` switches server-side expiry off entirely;
sessions then live until they are destroyed or the store loses them.

The time a session was last used is kept **by the store**, not inside the
session value. That is what makes the policy affordable: were it a key in the
hash table, every request — including the concurrent static-asset requests a
single page load fans out — would become a writer of the session. Instead the
store protocol has an operation that updates nothing but the time (one index
entry for the in-memory store, one column for the database store).

It is also not a repurposed `updated_at`: the database store owns a column of
its own and writes it on every store *and* every touch. A column maintained by
something else is not written when a request only reads, which under an
idle-timeout policy would expire exactly the users who are actively browsing.

### Removed twice over, on purpose

- **Lazily, when an expired session is presented.** The decision is made on
  every request from the stored timestamp, so an expired session is *never*
  honoured, whatever the sweeper is doing.
- **By a periodic sweeper thread**, started from the framework's startup hook
  and stopped from its shutdown hook, which walks the live ids every
  `*session-sweep-interval*` seconds and removes the ones that are past the
  limit. Without it, a session nobody comes back for would never be freed.

Stopping the server does **not** wait for the current interval to elapse, so a
long interval costs nothing at shutdown.

### A hard kill runs no hooks

`SIGKILL`, a power cut or a crash take the process without running the
shutdown hook. That is accounted for rather than handled:

- with the in-memory store the sessions die with the process, so there is
  nothing left to clean up;
- with a persistent store the rows stay behind, and are removed by the next
  process's sweeper or by the lazy deletion if someone presents one of those
  ids. Nothing accumulates permanently, and no expired session is ever
  honoured.

### Why the sweeper is not a job

clails has a job queue, and "run something every five minutes" sounds like a
job. It cannot be one, for three independent reasons:

1. **The worker is a different process.** Jobs are claimed by `clails
   job:work`, which runs outside the web server, and the default store keeps
   its sessions in the memory of the server process.
2. **There is no recurring schedule.** The queue runs a job once, at or after a
   given time. A job would have to re-enqueue itself, and one lost enqueue
   would silently end cleanup for ever.
3. **It requires a database table.** Session expiry has to work for the
   default configuration, which has no database.

## 6. Stores

`*session-store*` accepts either a class deriving from clails'
`clails/middleware/session/store:<session-store>` or a lack session store
structure. Both are driven by the session stage in the same way; only a clails
derivation can implement the store protocol's fourth operation
(`touch-session`), which is what records when a session was last used — a lack
structure cannot inherit from a CLOS class, so it has no last-access time and
no idle expiry.

### In-memory (the default)

`NIL` means a fresh in-memory store is created when the stack is built. It is
right for development and for a single process, but sessions are lost when the
process stops and are not shared with a second process.

### Database (the production recommendation)

Sessions survive a restart and are shared by every process that reads the same
table.

```common-lisp
(setf clails/middleware/session-middleware:*session-store*
      (clails/middleware/session/store/db:make-db-session-store))
```

The store takes a connection of its own for each operation and gives it back
when it is done: the session stage sits *outside* the transaction stage, so
writing the session through the request's connection would enrol it in the
application's transaction — an application rollback would silently roll the
session back with it.

**Only values that can be printed and read back may go into a session kept in
a table** — strings, numbers, symbols, lists, vectors, hash-tables of those. A
class instance or a stream cannot be stored, and the store signals an error
rather than writing text it could not read back. (This is the one restriction
the in-memory store does not have; see also section 7 on `current-user`.)

#### Creating the table

```bash
clails db:create-session-table
```

- **The definition is a file in your project: `db/session-table.lisp`**, copied
  in by `clails new`. You can read and edit it; the store reads the column
  names from the same file, so renaming a column there moves both halves at
  once. A project created before that file existed falls back to the
  framework's own definition, which is the same content.
- **It is not a migration.** The file is data, read and never evaluated. The
  table does not appear in the migration history or in `db/schema.lisp`, and
  `clails db:migrate` and `clails db:status` neither create nor touch it. That
  is deliberate: the session table is framework bookkeeping, not part of your
  schema.
- **One step, and safe to run twice.** The command renders one `CREATE TABLE
  IF NOT EXISTS` and runs it; running it again does nothing and keeps the
  sessions that are already there. There is no intermediate file to apply
  afterwards.
- **Dialect differences are handled when the statement is rendered**, so the
  same definition file works for SQLite3, MySQL and PostgreSQL (the spelling
  of `datetime` against `timestamp`, for instance, is chosen per dialect).
- **There is deliberately no command to drop the table.** The table holds no
  application data, and a mistyped drop command would log every user out at
  once; removing it is a `DROP TABLE` in the database, where an operation that
  destructive belongs.

In a generated project the make target is `make db.create-session-table`, and
the step is listed in the project's README under "Setup Database".

### Another store

Subclass `<session-store>`, implement `fetch-session`, `store-session`,
`remove-session` (and, if your medium can do better than read-modify-write,
`touch-session`) and put an instance in `*session-store*`. The base class
provides a default `touch-session`, so idle expiry keeps working for a store
that does not implement it.

## 7. Concurrent requests on one session

### What the framework guarantees

A single page load fans out several requests carrying the same session cookie,
so concurrent access to one session is the normal case, not an edge case. The
session stage therefore wraps the configured store so that access to one
session is serialised: **the session itself can no longer be corrupted** — no
lost table, no half-written value, whatever the browser does.

### What it does not guarantee

Serialising each read and each write does **not** make a *sequence* of them
atomic. Two requests that both read a value, change it and write it back can
still end up applying only one of the two changes. It is a specification, not
a defect — Rails and Django are in the same position.

The alternative — holding the lock for the *whole* request — was considered and
deliberately not taken: it would make a single user's own requests queue up
behind each other, and the store it would protect is the in-memory one, which
is not a production configuration in the first place. A deployment that
outgrows it moves to a shared store and more processes, where a per-request
lock in one image would not help anyway.

Where it matters, make the sequence atomic with `with-session-lock`:

```common-lisp
(with-session-lock (controller)
  (let ((count (or (gethash "count" (session controller)) 0)))
    (setf (gethash "count" (session controller)) (1+ count))))
```

Use it for anything that reads the session and then writes what it read: a
counter, appending to a list, a conditional update. Three things to know:

- **Keep the body short.** Other requests on the *same* session wait for it to
  finish, so a query or an HTTP call belongs outside the lock. Requests on
  other sessions are not affected at all.
- **Nesting is safe.** The lock is recursive.
- **It is a lock in this process only.** See below.

### Several processes: last writer wins

With a database (or, later, Redis) store shared by several processes, two
requests on the same session handled by *different* processes can still lose
one of the two write-backs: the whole session value is written, so the later
write replaces the earlier one. This is documented behaviour rather than a
defect — again the position Rails and Django take — and clails deliberately
adds no optimistic locking and no compare-and-set.

- It does not arise in a single-process deployment, which is what the default
  configuration is.
- **`with-session-lock` does not help here.** It is a lock inside one image;
  it holds back requests in this process and knows nothing about the others.

## 8. `current-user`: an extension point, not an auth system

`current-user` is a thin pair of accessors built directly on top of `session`:

```common-lisp
(current-user controller)              ; => whatever you last stored, or NIL
(setf (current-user controller) user)  ; store `user` as the logged-in user
(setf (current-user controller) nil)   ; "log out"
```

Internally it reads and writes one reserved key (`"clails.current-user"`)
inside the same hash table `session` exposes — there is no separate storage and
no user-model requirement. `user` can be anything your application finds
useful: a plist of `:id`/`:name`, just an integer id you re-look-up per
request, or a model instance.

**One caveat if you use the database session store:** whatever you put there is
part of the session value, so it has to be printable and readable (see
section 6). A plist or an id qualifies; a model instance does not. Storing an
id and looking the record up per request is the portable choice.

### Illustrative login/logout example

**This example is intentionally minimal and is *not* production-security
grade.** It shows the shape of the API; it does no password hashing, no
timing-safe comparison and no rate limiting — you must add all of that
yourself, or use a dedicated library.

```common-lisp
(defclass <session-controller> (<rest-controller>)
  ())

;; POST /login  { "email": "...", "password": "..." }
(defmethod do-post ((controller <session-controller>))
  (let* ((email (param controller "email"))
         (password (param controller "password"))
         ;; find-user-by-email / verify-password are YOUR project's code;
         ;; clails does not provide user lookup or password verification.
         (user (find-user-by-email email)))
    (if (and user (verify-password user password))
        (progn
          ;; a new id for the newly privileged session: see section 4
          (session-regenerate-id controller)
          (setf (current-user controller) (list :id (ref user :id)
                                                :email (ref user :email)))
          (set-response controller '((:status . "ok"))))
        (progn
          (setf (slot-value controller 'code) 401)
          (set-response controller '((:status . "error")
                                     (:message . "invalid credentials")))))))

;; DELETE /login (logout)
(defmethod do-delete ((controller <session-controller>))
  (set-response controller '((:status . "ok")))
  (session-destroy controller))
```

And a controller that requires a logged-in user:

```common-lisp
(defclass <account-controller> (<web-controller>)
  ())

(defmethod do-get ((controller <account-controller>))
  (let ((user (current-user controller)))
    (if user
        (set-view controller "account/show.html" `(:user ,user))
        (set-redirect controller "/login"))))
```

Because this check is just plain Lisp, you are free to factor it into a helper
or a `:before` method — clails does not impose an authorization pattern.

## 9. Migrating an existing project

`clails new` writes a project's configuration **once**. Nothing in this release
reaches a project that already exists, so the steps below are manual and all of
them are optional — a project that changes nothing keeps working, with sessions
off.

1. **Add the session settings** to `app/config/environment.lisp`. The easiest
   way is to generate a throwaway project (`clails new scratch`) and copy the
   "Sessions" block out of its `app/config/environment.lisp`, including the
   `setup-session/<environment>` functions.
2. **Call the per-environment part at boot.** The Secure flag is read while the
   middleware stack is built, which happens *before* the first startup hook
   runs, so a startup hook is too late. The generated `clails.boot` calls
   `(<project>/config/environment:initialize-session-config)` right after
   `resolve-project-environment`; add that line to your own `clails.boot` (and
   export the function from the configuration package). If you skip this step,
   remember that the cookie will not be marked Secure in production.
3. **If you replaced `*clails-middleware-stack*` wholesale**, your stack has no
   session stage, and adding the configuration above will not give you one.
   Switch to `add-middleware-before` / `add-middleware-after` for your own
   stages, so that the framework's stages stay where they belong. See the
   [Environment Guide](environment.md).
4. **To keep sessions in the database**, copy `db/session-table.lisp` out of a
   generated project (or rely on the framework's identical built-in
   definition), run `clails db:create-session-table` per environment, and set
   `*session-store*` to `(make-db-session-store)`. Add the
   `db.create-session-table` target to your project's `Makefile` if you want
   the make shortcut: a generated `Makefile` and `README.md` are copied once
   too, so neither reaches an existing project.
5. **Expect the cookie defaults to have changed.** Sessions you had before are
   not carried over: the cookie name is no longer the library's
   (`lack.session`), so a browser holding an old cookie starts a new session
   once — i.e. logged-in users are logged out one time. The new cookie is
   HttpOnly, states `SameSite=Lax` (so it is no longer sent with cross-site
   POSTs) and carries no expiry date. To keep the old behaviour, build the
   state yourself and pass `:cookie-key "lack.session"` (see section 2).
6. **The production log destinations were corrected** in the generated
   `app/config/logger.lisp`: the web-access destination used to be registered
   under the name `:sql`, which left `:web-access` unregistered and sent SQL
   records to `logs/access.log` while `logs/sql.log` stayed empty. The fix is
   in the template, so it does not reach an existing project — compare your
   `setup-logger/production` against a freshly generated one and make sure
   `:sql`, `:web-access`, `:audit` and `:task` are each registered exactly
   once. This matters beyond logging: the `:audit` destination is where clails
   records rejected requests.

## Summary

1. A generated project has sessions **on**; the framework's default is **off**,
   so existing projects are unaffected until their configuration says
   otherwise.
2. `(session controller)` is a request-scoped, cookie-backed hash table. Keys
   beginning with `clails.` are reserved for the framework.
3. Sessions expire after **30 minutes of disuse** by default, and are removed
   both lazily and by a periodic sweeper. The cookie carries no expiry date, by
   design.
4. The cookie is HttpOnly and `SameSite=Lax`, with a name that does not
   advertise the implementation. **Secure is off by default and is turned on
   per environment by the project's configuration** — on in production, off for
   plain-HTTP development.
5. The in-memory store is the default; the database store is the production
   recommendation, and its table is created once with
   `clails db:create-session-table`.
6. Concurrent requests cannot corrupt a session, but a read-modify-write can
   still lose an update — use `with-session-lock`. Across several processes the
   last writer wins.
7. `current-user` is plumbing for "whoever is logged in". Login logic,
   password handling and authorization are your project's responsibility, and
   CSRF protection is not part of this release.
